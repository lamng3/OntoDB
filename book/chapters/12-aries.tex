\chapter{ARIES}
\label{ch:aries}

ARIES (Algorithm for Recovery and Isolation Exploiting Semantics), published by
Mohan, Haderle, Lindsay, Pirahesh, and Schwarz in 1992 \cite{aries}, is the
recovery algorithm behind most disk-based database systems. It supports steal
and no force, fine-grained locking, and partial rollbacks, and it recovers
correctly even if the system crashes again \emph{during} recovery. Its central
idea fits in three words: \textbf{repeat history, then undo}.

\section{The data structures}

\begin{description}[leftmargin=1.2em]
\item[Log records] as in \cref{ch:wal}: LSN, transaction id, prevLSN, and type-specific fields.
\item[pageLSN] on every page: the LSN of the last change applied to it.
\item[Transaction table] for every active transaction: its status and \term{lastLSN}, the LSN of its most recent record.
\item[Dirty page table] for every page dirty in the buffer pool: its \term{recLSN}, the LSN of the first record that made it dirty since it was last read from disk. Any change to the page before recLSN is already on disk.
\item[Compensation log records (CLRs)] written when a change is undone. A CLR describes the undo, and carries \term{undoNextLSN}: the next record of that transaction still to undo.
\end{description}

\section{Checkpoints}

Without checkpoints, recovery would read the log from the beginning of time. A
\term{fuzzy checkpoint} writes the transaction table and the dirty page table
into the log without stopping the system or forcing any pages, and records the
checkpoint's LSN in a well-known place. Recovery then starts from the last
checkpoint: the tables in it tell analysis everything that happened before.

\section{Pass 1: Analysis}

Scan the log forward from the last checkpoint, rebuilding the two tables as of
the crash:

\begin{itemize}
\item On any record of a transaction not in the table, add it. Update its lastLSN.
\item On a commit, mark it committed; on an end record, remove it.
\item On an update or CLR for a page not in the dirty page table, add the page with recLSN = this LSN.
\end{itemize}

At the end, every transaction still in the table without a commit is a
\term{loser}. The \term{redoLSN} is the smallest recLSN in the dirty page table:
no earlier change can be missing from disk.

\section{Pass 2: Redo}

Scan forward from redoLSN, and reapply every update and every CLR, for winners
and losers alike, unless the change is provably already on disk:

\begin{lstlisting}[language=pseudo]
for each update or CLR record r, from redoLSN forward:
  if r.page not in dirty page table:          skip   // page was clean at the crash
  if dirtyPageTable[r.page].recLSN > r.lsn:   skip   // flushed after r
  fetch page
  if page.pageLSN >= r.lsn:                   skip   // r already on the page
  apply r to the page; page.pageLSN = r.lsn
\end{lstlisting}

Redo \textbf{repeats history}: it brings the database to exactly its state at
the crash, uncommitted changes included. That sounds wasteful, but it makes undo
simple: undo now starts from a precise, known state, and can use the same
logical operations that a normal abort uses.

\section{Pass 3: Undo}

Undo the losers, newest change first, across all of them at once:

\begin{lstlisting}[language=pseudo]
toUndo = { lastLSN of each loser }
while toUndo is not empty:
  r = record with the largest LSN in toUndo; remove it
  if r is a CLR:
    if r.undoNextLSN exists: add r.undoNextLSN to toUndo
    else: write an end record for r.txn
  else if r is an update:
    undo r; write CLR(undoNextLSN = r.prevLSN)
    if r.prevLSN exists: add r.prevLSN to toUndo
    else: write an end record for r.txn
\end{lstlisting}

\begin{keyidea}
A CLR is redone but never undone. If the system crashes during undo, the next
recovery redoes the CLRs (history repeats), then follows their undoNextLSN
pointers past everything already undone. Recovery work is therefore bounded no
matter how many times the system crashes during recovery.
\end{keyidea}

\section{A worked example}

Two transactions run. $T_1$ commits; $T_2$ does not. The buffer pool happened
to write page P2 (stealing $T_2$'s uncommitted change), but never wrote P1.

\begin{center}
\begin{tabular}{@{}rlll@{}}
\toprule
LSN & Transaction & Record & prevLSN \\
\midrule
10 & $T_1$ & update P1 & --- \\
20 & $T_2$ & update P2 & --- \\
30 & $T_1$ & commit & 10 \\
40 & $T_2$ & update P1 & 20 \\
\multicolumn{4}{@{}l}{\emph{crash.} On disk: P1 has pageLSN 0; P2 has pageLSN 20.} \\
\bottomrule
\end{tabular}
\end{center}

\paragraph{Analysis.} $T_1$ committed; $T_2$ is a loser with lastLSN 40. The
dirty page table is \{P1: recLSN 10, P2: recLSN 20\}, so redoLSN is 10.

\paragraph{Redo.} LSN 10 on P1: pageLSN 0 $<$ 10, so redo; P1's pageLSN becomes
10. LSN 20 on P2: pageLSN 20 $\ge$ 20, so skip; the stolen write already put it
there. LSN 40 on P1: pageLSN 10 $<$ 40, so redo; pageLSN becomes 40. The
database is now exactly as it was at the crash, including $T_2$'s two changes.

\paragraph{Undo.} toUndo = \{40\}. Undo LSN 40 on P1, write CLR 50 with
undoNextLSN 20. Undo LSN 20 on P2, write CLR 60 with no undoNextLSN, then an end
record for $T_2$. $T_1$'s change survives; $T_2$ left no trace.

If the system had crashed right after CLR 50, the next analysis would find $T_2$
with lastLSN 50; redo would reapply CLR 50; undo would read CLR 50, jump straight
to LSN 20, and never undo LSN 40 a second time.

\section{Structure changes: nested top actions}

A B+ tree split moves keys between pages. Suppose $T$ inserts a key, which
splits a leaf, and later aborts. Undoing ``the split'' would be wrong: another
transaction may have committed an insert into the new leaf since then. The
split is a change to the \emph{structure}, which is valid regardless of who
caused it; only the \emph{logical} insert belongs to $T$.

ARIES logs a split as a \term{nested top action}: the split's page records,
followed by a dummy CLR whose undoNextLSN points to the record just before the
split. Redo replays the split like any other change. Undo, following the dummy
CLR, skips over it. The logical ``insert key $k$'' is logged separately, and its
undo is the logical ``delete key $k$'', performed wherever that key now lives,
which is why undo in ARIES is logical while redo is physical.

\section{Undo must survive being repeated}

Undo is logical: ``take back insert $t$'' becomes ``delete $t$''. A crash can
strike in the middle of that delete, and the next recovery will run it again,
because the CLR is written after the change. So every logical undo must give
the right answer when it runs against a state where it already half happened.

In a triple store, one triple lives in several indexes. Deleting it is three
tree operations. A page group (\cref{ch:wal}) makes each of the three atomic,
but nothing makes the three atomic together. If the crash comes after SPO has
lost the triple but before OSP has, the repeated undo meets a triple that is
absent from SPO and present in OSP.

\begin{ontodb}[: ARIES]
On open, \code{LogRecovery} (\code{src/recovery/recovery.cpp}) reads the
whole log and runs the three passes:

\begin{description}[leftmargin=1.2em]
\item[Analysis.] A transaction with a commit record is a winner. One with a begin, an update, or a CLR but neither a commit nor an abort record is a loser; an abort record is written when an abort or a recovery undo finishes, so it doubles as ARIES's end record. Checkpoints are sharp, so the dirty page table starts at the last checkpoint: each page's first page record after it is the page's recLSN, and the smallest is the redo LSN.
\item[Redo.] For each page record from the redo LSN on, fetch the page through the pool's raw interface, so redo is not logged again, and copy the image if the record is newer than the pageLSN. Redo is physical and the same for every page.
\item[Undo.] The catalog is opened only after redo, since redo may be what rebuilds page 0. Each loser's update records are undone newest first through the same \code{UndoChain} a normal abort uses: delete what it inserted, insert what it deleted, a CLR after each, then an abort record.
\end{description}

\code{\textbackslash checkpoint} on a page store is \code{CheckpointManager::Checkpoint}:
write every dirty page (the pool forces the log first), then append the
checkpoint record listing the active transactions, and force it.

\code{IndexedStore::Insert} and \code{Delete} change every index that
disagrees, rather than asking the first index and stopping. Repeating an
interrupted undo therefore repairs the indexes it did not reach.
\end{ontodb}

\section{The crash harness}

The bar for this part is \code{scripts/crashtest --seeds 200}. For each seed,
a child process opens a real store: a database file, three trees with at most
four keys a node so that a few dozen triples split and merge pages, a 16-frame
pool so pages are stolen, and the log. The parent feeds it a random schedule
of transactions, then kills it. A third of the seeds die between operations.
The rest die at a randomly chosen reach of a named crash point (inside a
split, inside a merge, or between a log flush and a page write), half of them
after flushing everything the log allows, so that any half-finished change that
\emph{could} reach the disk does. The parent then reopens the store (a torn
last record is cut off, then the three passes) and compares it with an oracle
that applied only acknowledged commits. It also checks every tree's
invariants, a point lookup for every triple, and that SPO, POS, and OSP hold
the same triples.

The harness is tested by breaking the store on purpose. Removing redo fails
30 of 30 seeds. Removing page groups fails 25 of 200, as broken trees and
indexes that disagree. Going back to the first-index-only \code{Insert} and
\code{Delete} fails 4 of 200, as POS or OSP holding a triple SPO lacks.

\begin{decision}{Physical redo, logical undo}
\dpart{Choice} Redo copies page images. Undo replays the inverse of each
logical triple change through the store, writing a CLR for each.
\dpart{Alternatives} Physical undo from before-images; logical redo of triple
changes.
\dpart{Why} This is ARIES's own split. Redo must work on pages that may be
inconsistent with each other, so it cannot depend on the tree's structure.
Undo runs after redo has repeated history and the tree is sound, and it must
take back one transaction's triple even if other transactions have since moved
it to a different page.
\dpart{Cost} Two kinds of record for one statement, and the store's operations
must be idempotent, since undo can be repeated after a crash part way through.
\end{decision}

\begin{decision}{A sharp checkpoint}
\dpart{Choice} \code{Checkpoint} flushes every dirty page, then writes the
checkpoint record with the active transactions. Updates must not run while it
does.
\dpart{Alternatives} ARIES's fuzzy checkpoint, which writes the transaction and
dirty page tables without flushing anything or stopping the system.
\dpart{Why} After a sharp checkpoint nothing older than its record needs redo,
so analysis builds the dirty page table from the page records after it, and
the checkpoint needs no table of its own. Fuzzy checkpoints are an
optimization to add once the three passes are known to be correct.
\dpart{Cost} Updates stall while every dirty page is written. The log is not
yet truncated after a checkpoint, so analysis still reads the whole file to
find losers that began before it.
\end{decision}

\begin{decision}{Recovery is tested against an oracle}
\dpart{Choice} A crash harness kills a real store at random points and at named
crash points, reopens it, and compares it with an oracle that applied only
acknowledged commits, plus structural checks. The harness is itself tested on
deliberately broken stores.
\dpart{Alternatives} Hand-written recovery scenarios only.
\dpart{Why} The bugs in recovery live in interleavings nobody thinks to write.
The first version of this harness only killed between operations on a
workload too small to split a page. It passed while a crash inside a split
could leave a broken tree. Making it grow deep trees and die inside
operations found that bug and the non-idempotent undo within minutes.
\dpart{Cost} Slow tests (about two minutes for 200 seeds), and failures that
need a seed to reproduce. Tree descents and the leaf iterator now fail with an
error on a cycle, so a corrupt store fails a seed rather than hanging the
harness.
\end{decision}

Abort by the log (plan 8.4), the sharp checkpoint (plan 8.5), the three passes
(plan 8.6), and the crash test (plan 8.7) run, and 200 seeds pass. What is

\end{status}

\begin{checkyourself}
\item In the worked example, suppose the pool had also written P1 after LSN 40. What does redo do now, and what does undo do?
\item Why does ARIES redo the losers' changes, only to undo them right after?
\item The system crashes after CLR 60 but before $T_2$'s end record. What does the next recovery do?
\item Why is a B+ tree split never undone, even when the transaction that caused it aborts?
\item What do the dirty page table's recLSNs let redo skip?
\item A loser inserted triple $t$. Recovery's undo deletes $t$ from SPO and POS, then the machine stops again. Why must the next recovery's undo still delete $t$ from OSP, and what would go wrong if \code{Delete} looked only at SPO?
\item Why does OntoDB open the catalog after redo instead of before analysis?
\item A crash harness passes 200 seeds. What else must be true before that means anything?
\end{checkyourself}
