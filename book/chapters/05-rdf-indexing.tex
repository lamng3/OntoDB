\chapter{Indexing RDF}
\label{ch:rdf-indexing}

A relational table has a schema, and each column can be indexed on its own.
An RDF store has one table with three columns, and a query can bind any subset
of them. This chapter shows how a triple store turns that into fixed-size keys
in B+ trees: first by replacing strings with integers, then by laying out the
integers so that byte order is query order, and finally by keeping more than
one ordering of the same triples.

\section{Dictionary encoding}

IRIs are long and repeated: the same predicate appears in millions of triples.
Storing strings in the index would waste space and make every comparison a
string comparison. Instead, a \term{dictionary} maps each distinct term to a
dense integer id, once.

\begin{center}
\begin{tabular}{@{}rl@{}}
\toprule
id & canonical spelling \\
\midrule
1 & \code{<http://example.edu/univ\#Alice>} \\
2 & \code{<http://www.w3.org/1999/02/22-rdf-syntax-ns\#type>} \\
3 & \code{<http://example.edu/univ\#Student>} \\
4 & \code{"Alice"} \\
\bottomrule
\end{tabular}
\end{center}

A triple becomes three integers, \code{(1, 2, 3)}. Comparing ids is one machine
instruction, and the index stores 24 bytes per triple regardless of how long
the IRIs are.

Two rules keep the dictionary correct:

\begin{itemize}
\item \textbf{One spelling per term.} The loader and the query binder must produce the same canonical text for the same term, or one IRI becomes two ids and every join on it silently fails. Escapes, datatype IRIs, and language tags are part of the spelling.
\item \textbf{Ids never change.} An id assigned once keeps its meaning across restarts. A log record that names id 18 must still mean the same term when it is replayed (\cref{ch:durability}).
\end{itemize}

\begin{ontodb}[: the dictionary]
Ids are 64-bit and start at 1; 0 is never a valid id, so a zeroed key never
names a real term, and the maximum value means ``unbound'' and is never
assigned (see the design decision below). A single codec
produces canonical spellings for both the loader and the binder: \code{<iri>},
\code{"lex"}, \code{"lex"@en}, \code{"lex"\^{}\^{}<datatype>}, and \code{\_:b0}.
Numeric literals compare by value in filters; everything else compares by id
for equality and by spelling for order.
\end{ontodb}

\section{A key whose bytes sort correctly}

A B+ tree compares keys. The fastest comparison is \code{memcmp} on raw bytes,
which works only if byte order equals the intended order. For a key made of
three unsigned integers, that requires \textbf{big-endian} encoding: the most
significant byte first.

\centering

\foreach \i in {8,...,15}{\node[draw,minimum width=0.5cm,minimum height=0.5cm,fill=ideabg] at (\i*0.5,0) {};}
\foreach \i in {16,...,23}{\node[draw,minimum width=0.5cm,minimum height=0.5cm,fill=statusbg] at (\i*0.5,0) {};}
\node at (1.75,0.55) {subject (8 bytes)};
\node at (5.75,0.55) {predicate (8 bytes)};
\node at (9.75,0.55) {object (8 bytes)};
\node at (0,-0.5) {0}; \node at (3.5,-0.5) {7}; \node at (4,-0.5) {8}; \node at (11.5,-0.5) {23};
\end{tikzpicture}
\caption{A 24-byte triple key: three big-endian unsigned 64-bit ids.}
\label{fig:key}
\end{figure}

Why big-endian: little-endian stores the least significant byte first, so the
id 256 (\code{00 01 00\ldots} in little-endian) would compare below the id 1
(\code{01 00 00\ldots}). With big-endian, integer order and byte order agree,
and the comparison needs no decoding at all.

\section{Prefix scans}

A triple pattern with some positions bound is a \emph{prefix} of the key, if the
bound positions come first. ``Every triple with subject 5'' is every key whose
first 8 bytes encode 5. Such a prefix is a contiguous range of keys, so a scan
is one descent plus a walk along leaves. The range is $[\text{lower},
\text{upper})$, where lower is the prefix padded with zeros and upper is the
prefix's last component plus one:

\begin{center}
\begin{tabular}{@{}cll@{}}
\toprule
Bound components & Lower bound & Upper bound (exclusive) \\
\midrule
0 & \code{(0, 0, 0)} & past every key \\
1 & \code{(5, 0, 0)} & \code{(6, 0, 0)} \\
2 & \code{(5, 7, 0)} & \code{(5, 8, 0)} \\
3 & \code{(5, 7, 9)} & \code{(5, 7, 10)} \\
\bottomrule
\end{tabular}
\end{center}

\section{One ordering is not enough}

An index ordered subject, predicate, object (SPO) serves any pattern whose bound
positions are a prefix of S-P-O. It does not serve ``which subjects have object
\code{Material}?'': the object is the last component, so the matching keys are
scattered across the whole tree. The fix is to store the same triples in more
than one order.

\begin{table}[ht]
\centering
\begin{tabular}{@{}ll@{}}
\toprule
Bound positions in the pattern & Answered as a prefix of \\
\midrule
subject & SPO \\
subject, predicate & SPO \\
predicate & POS \\
predicate, object & POS \\
object & OSP \\
object, subject & OSP \\
all three & any (a point lookup) \\
none & any (a full scan) \\
\bottomrule
\end{tabular}
\caption{Three permutations (SPO, POS, OSP) make every bound/unbound combination a prefix scan.}
\label{tab:perm}
\end{table}

Hexastore \cite{hexastore} keeps all six permutations; RDF-3X \cite{rdf3x} also
keeps six but compresses them heavily and adds aggregated indexes. Each
permutation is another full copy of the triples, so the right number is a
measurement, not a default: three cover every pattern as a prefix, and the
other three only add sorted orders that some joins can exploit.

\begin{keyidea}
Extra permutations change the \emph{cost} of answering a pattern, never the
\emph{answer}. With only SPO, every pattern is still answerable by scanning and
filtering; the other permutations turn scans into prefix ranges.
\end{keyidea}

\begin{ontodb}[: keys, permutations, and the catalog]
OntoDB's \code{TripleKey} is exactly \cref{fig:key}: three big-endian
\code{uint64}s, compared with \code{memcmp}. \code{PrefixLower(key, n)} and
\code{PrefixUpper(key, n)} produce the bounds for $n = 0, 1, 2, 3$ bound
components. The upper bound adds one to the prefix, read as a big-endian
number, carrying left. When nothing lies above the prefix ($n = 0$, or every
bound id is the maximum) it saturates to the all-\code{0xFF} key, three copies of
\code{INVALID\_TERM\_ID}, which the dictionary never assigns. The catalog names three B+ tree roots, \code{"spo"}, \code{"pos"},
and \code{"osp"}, and an insert or delete updates every permutation the catalog
has, or none. The plan builds SPO first and then \emph{measures} whether POS and
OSP pay for their space on real SPARQL workloads before adding them.
\end{ontodb}

\begin{decision}{Ids start at 1; 0 and the maximum are reserved}
\dpart{Choice} Term ids are dense 64-bit integers starting at 1. Id 0 is never
used. The largest id, \code{INVALID\_TERM\_ID} ($2^{64}-1$), is the engine-wide
marker for ``unbound'': a row slot that no pattern has filled, a pattern
position that is a variable. \code{Dictionary::CheckAssignable} refuses to hand
it out, so every dictionary enforces the reservation, not just the
arithmetic.
\dpart{Alternatives} An \code{optional} per row slot (a flag beside every id),
or a separate bitmap of which slots are bound.
\dpart{Why} A row stays a plain array of \code{uint64}, which joins compare and
hash directly. And because no stored triple can contain the maximum id, the
all-\code{0xFF} key lies above every real key, which the prefix bounds use.
\dpart{Cost} Two ids out of $2^{64}$, and a contract every dictionary must keep;
a dictionary that skipped the check could hand a real term an id that every
operator reads as ``unbound''.
\end{decision}

\begin{decision}{The dictionary is built from the engine's own pages}
\dpart{Choice} On disk, spellings live in the term heap. Two B+ trees index
them, both with ordinary 24-byte triple keys: one keyed
$(\textit{id}, \textit{page}, \textit{slot})$, so a prefix scan on the id finds
the record; one keyed $(\textit{hash}, \textit{id}, 0)$, so a prefix scan on a
spelling's hash lists candidate ids, each checked against the heap. A header
page holds the term count and the three page ids.
\dpart{Alternatives} Keep the dictionary in memory and rebuild its hash maps
from the heap at every open; or write a dedicated on-disk hash index, such as
extendible hashing.
\dpart{Why} It reuses parts that are already tested, works when the
dictionary is larger than memory, and needs nothing rebuilt at startup.
Comparing the spelling makes hash collisions harmless.
\dpart{Cost} Looking up a spelling is two tree descents and a heap read,
against one probe of an in-memory hash table, and each term costs 48 bytes of
index on top of its spelling. A memory cache in front is the obvious
optimization if lookups dominate a load.
\end{decision}

\begin{decision}{A fixed hash function}
\dpart{Choice} The spelling hash is 64-bit FNV-1a, written out in the code.
\dpart{Alternatives} \code{std::hash}, or a faster modern hash from a library.
\dpart{Why} A hash stored on disk must give the same value in every build, on
every machine, forever. \code{std::hash} promises none of that; a different
standard library would silently make every stored entry unreachable.
\dpart{Cost} FNV-1a is slower and mixes less well than newer hashes; with
spellings this short, and collisions resolved by comparison, neither matters.
\end{decision}

\begin{decision}{Big-endian keys, compared with \code{memcmp}}
\dpart{Choice} Each id is written most significant byte first, so comparing
the 24 bytes with \code{memcmp} gives numeric $(s, p, o)$ order.
\code{Compare} returns the sign of \code{memcmp}.
\dpart{Alternatives} Store native integers and compare by decoding three
\code{uint64}s; or store little-endian and use a custom comparator.
\dpart{Why} Pages, binary search, and the iterator can treat keys as opaque
bytes, with no knowledge of their structure. Note the contrast: the pageLSN and
log records use the machine's own byte order (little-endian on x86 and ARM),
because nothing ever compares them as bytes.
\dpart{Cost} A byte swap on every encode and decode on little-endian machines,
which is negligible.
\end{decision}

\begin{decision}{The upper bound saturates instead of failing}
\dpart{Choice} \code{PrefixUpper} adds one to the prefix with carry. When there
is nothing above the prefix ($n = 0$, or every bound id is the maximum), it
returns the all-\code{0xFF} key rather than an error or a flag.
\dpart{Alternatives} Return an optional bound meaning ``to the end of the
tree'', or a flag the iterator checks.
\dpart{Why} One key type for both ends keeps the scan loop to a single test:
stop when the key reaches upper. Saturation is safe because of the reserved
maximum id above.
\dpart{Cost} The scan's correctness now depends on the dictionary's contract,
which is why that contract is checked in code and tested.
\end{decision}

\begin{decision}{The catalog points at header pages, not roots}
\dpart{Choice} The catalog, page 0, maps a name (\code{"spo"}) to the page id
of that tree's \emph{header} page; the header page holds the tree's current
root.
\dpart{Alternatives} Store each tree's root page id in the catalog directly.
\dpart{Why} A root changes whenever the root splits or collapses. With a header
page in between, only the tree's own header page changes, and the catalog is
written only when an index is created or dropped.
\dpart{Cost} One more page read to find a root, though the header pages are
small in number and stay in the pool.
\end{decision}

\begin{decision}{The catalog claims page 0 by writing it}
\dpart{Choice} On first open, the catalog finds page 0 all zeros, writes a
magic number, an empty table, and an \code{INVALID\_PAGE\_ID} dictionary root,
and writes the page to the file immediately. A page 0 with other contents is
refused, not reinterpreted.
\dpart{Alternatives} Allocate the catalog like any other page and remember its
id somewhere, or trust that page 0 is the catalog.
\dpart{Why} The disk manager's allocation record is the file's length. Writing
page 0 at once makes the file one page long, so no later allocation can hand
out id 0 to something else. The magic number distinguishes ``never
initialized'' from ``a catalog whose dictionary root happens to be 0''.
\dpart{Cost} An extra page write when a database is created.
\end{decision}

\item Encode the id 258 as 8 big-endian bytes and as 8 little-endian bytes. Which encoding sorts correctly under \code{memcmp} against the id 3?
\item Give the lower and upper bounds for the pattern \code{(5, ?, ?)} and for \code{(5, 7, ?)}.
\item What is \code{PrefixUpper} of the key $(5, 2^{64}-1, 9)$ with $n = 2$? With $n = 1$ and subject $2^{64}-1$?
\item Which permutation serves \code{?s ?p <Material>}? Which serves \code{<Alice> ?p <Student>}?
\item Why must the loader and the binder share one canonical spelling for terms? Give a literal that two careless implementations might spell differently.
\item What would go wrong if the dictionary assigned $2^{64}-1$ to a real term?
\item Two different spellings have the same 64-bit hash. What does the disk dictionary do when you look up the second one?
\item Why does the catalog record each index's header page rather than its root? How often does the catalog page change?
\end{checkyourself}
